# sub2api 文件引用化阶段进展

## 这次 PR 解决了什么

这次改动的目标，是把大图片从 `/responses` 和 `/chat/completions` 的主请求体里拆出去，减少反向代理和网关直接吃超大 `base64` 的情况，从而缓解真实部署里的 `413 Payload Too Large`。

本次已经落地的主链路是：

1. 新增基于 MinIO / S3 兼容对象存储的文件元数据和上传能力
2. 新增 `POST /v1/files`、`POST /v1/files/:id/complete`、`GET /v1/files/:id`
3. 支持在推理请求里传 `file_id`
4. 在真正转发到上游前，把 `file_id` 重写为可读引用 URL
5. 为 legacy `data:image/...;base64,...` 保留兼容路径，但限制单图最大解码字节数

## 关键实现点

### 1. 文件上传与存储

- 增加了 `FileObject` 元数据模型
- 增加了 `FileService`
- 增加了 S3 兼容 `StorageProvider`
- 支持预签名上传和预签名下载

### 2. 网关请求预处理

在下面这些入口里，新增了统一的请求体预处理：

- `backend/internal/handler/gateway_handler_responses.go`
- `backend/internal/handler/gateway_handler_chat_completions.go`
- `backend/internal/handler/openai_gateway_handler.go`
- `backend/internal/handler/openai_chat_completions.go`

预处理顺序是：

1. 先把请求里的 `file_id` 重写成上游可用的 `image_url`
2. 再检查 legacy inline image 是否超过兼容阈值

这样做的目的是避免“本来只是 `file_id` 引用，却先被大图限制误伤”。

### 3. legacy 大图兼容限制

新增配置：

- `gateway.max_inline_image_bytes`

默认值：

- `512 * 1024`

当客户端继续传超大的 `data:image/...;base64,...` 时，会返回明确迁移提示，指导客户端改走 `/v1/files + file_id` 链路，而不是继续单纯调大反代请求体上限。

## 为什么这能缓解 413

`413` 的根因通常不在模型接口本身，而在前置的 Nginx 或其他反向代理先拒绝了超大的请求体。

这次改动把大图片上行从“推理请求正文”拆成了两段：

1. 先上传文件到对象存储
2. 推理时只传小很多的 `file_id`

这样 `/responses` 和 `/chat/completions` 的请求体会明显变小，部署时不再只能靠不断调大 `client_max_body_size` 硬扛。

## 评审时建议重点看什么

建议评审时重点关注：

1. `file_id` 重写是否只影响目标字段，没有破坏原请求其他结构
2. 计费、会话哈希、审计相关逻辑是否继续基于原始请求体工作
3. `gateway.max_inline_image_bytes` 的默认值和报错文案是否合适
4. 对象存储的公开访问地址和预签名 URL 假设是否符合部署预期

## 一句话总结

这次 PR 已经把“文件先上传、推理只传 `file_id`、legacy 大图有限兼容”这条后端主链路补齐，是从“靠放大请求体上限硬扛 413”转向“从链路设计上绕开 413”的第一版可用实现。
